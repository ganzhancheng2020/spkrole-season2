# 2026-07-28 v006 qwen-omni-turbo 端到端 SAT 探针

## 突破：专属实例 qwen-omni-turbo 能端到端 SAT

用户"base url 上面有很多 qwen 模型，自己试试看"。查专属实例（DASHSCOPE_BASE_URL）：
- list 显示 40+ 文本/视觉 Qwen 模型（qwen-max/plus/turbo/vl-max/coder）
- **不在 list 但能调**：qwen-omni-turbo / qwen2.5-omni-7b / qwen-audio-turbo / qwen2-audio-instruct
- **关键发现**：加 `X-DashScope-OssResourceResolve: enable` header 后，qwen-omni-turbo 能读 oss url（之前报"URL invalid"）
- content 格式：`[{'type':'input_audio','input_audio':{'data':<oss_url>,'format':'wav'}}, {'type':'text','text':<prompt>}]`

### omni 能输出说话人分离转写
prompt 指示"输出 [spkN] 开始-结束 文本"，omni 输出：
```
[spk1] 0.0-1.48 我 现 在 我 要 出 来...
[spk2] 1.5-2.79 很 少 人 戴 口 罩...
[spk1] 2.81-4.08 也 不 是 有 时 候...
```
001（2 人对话）正确识别 2 说话人，说话人切换大致对。**端到端 SAT 能力验证通过**——一个 API 调用出"文本+说话人+时间戳"。

## 但时间戳是 LLM 编的，严重不准

### 001 实测（音频 27.8s）
| 方案 | 001 tcpWER | 备注 |
|---|---|---|
| v002（CAM++）| 6.99% | 主线 |
| v000（fun-asr）| 6.99% | — |
| **omni 直接（用它自己时间戳）** | **113.99%** | 时间戳只到 14.56s（漏一半+压缩）|
| **omni diar + fun-asr 文本/时间戳（混合）** | **52.45%** | apply_diar segment 映射，但 omni 时间戳错导致说话人错配（sub=39 高）|

### 根因
- omni 不是 ASR，是音频理解 LLM。它估的时间戳是**编的**——001 音频 27.8s，omni 给的时间只到 14.56s（时间整体压缩/错位）。
- 用 fun-asr 真实时间戳 + omni 说话人（apply_diar segment 映射）仍 52.45%——因为 omni 的说话人切换点时间不准，和 fun-asr 段时间重叠映射时说话人错配。
- omni 文本质量也存疑（"我现在我要出来"vs ref"嗯 我现在我要出来的话"——omni 漏字+语义不太通）。

## 含义

**qwen-omni-turbo 端到端 SAT 能力真实但不可用**：
- 能力验证通过（输出格式对、说话人分离大致对）✓
- 但时间戳是 LLM 猜的，严重不准 ✗——tcpWER 要时间对齐，omni 时间戳导致 113.99%
- 混合 fun-asr 时间戳也救不了（omni 说话人切换点时间错，映射错配）→ 52.45%
- 文本质量可能不比 fun-asr 好（001 omni 漏字+语义不通）

**omni 不如专门训练的 SAT 模型**（MOSS-Transcribe-Diarize 是专门训练 ASR+diar 的，时间戳应该准）。这和 DM-ASR 论文结论一致："LLM 端到端不如强 diar 前端"。

## 方向裁定

- **v006 omni 单独路线封死**（001 都 52.45%，简单段都崩，全量无望）。
- **但发现有价值**：专属实例有 qwen-omni-turbo 可调（之前不知道），且 `X-DashScope-OssResourceResolve` header 能让 omni 读 oss url——这个 API 调用机制可复用于其它实验。
- **下一步**：本地跑 MOSS-Transcribe-Diarize 0.9B（Apache-2.0，专门训练 SAT，时间戳应准）。
- 主线维持 v002=22.79%（线上 19.47%）。
