### ★ D10. 修复本地评估能力（**最高优先，其余方向的前提**）

**问题**：仿真微调路线下**没有任何可信的本地判据**。
- `holdout-24` 两个数据点迁移率 **+233%（v031）/ −156%（v032）** → 无预测力（24 段 / 4393 词）
- 全 dev **不可用** —— 82 段是仿真素材来源，对微调模型不干净
- 重尾关卡在 24 段上无意义（剔 top-3 = 去掉 1/8 样本）

**后果**：每次提交都是在拿额度做二分查找。v032→v033 就花了两次额度才归因出一个变量。

**候选做法（未验证）**：
① 换切分比例（如 60/46），用更大的留出集换更小的训练素材池；
② 对同一模型跑多组切分取方差，先量清 holdout-24 的噪声水平再决定信不信；
③ 造「仿真验证集」—— 用 holdout-24 的素材另合成一批，专测微调模型（但仍是仿真域，非真实域）。

⚠️ 三条都有明显缺陷，**这个问题目前没有干净解**，需要先想清楚再动手。

### ★ D11. 微调过程监控（观测验证集 loss / 早停 / 调参）

**动机**：v032 的失败是**过训还是伪影**至今未分辨。现配方固定 2 epoch，
800 条 = 400 步、3000 条 = 1500 步，**训练时不看任何验证指标**，训完才评测。

**要做的**：训练中周期性在 holdout 上算 loss，观察是否出现「训练 loss 降、验证 loss 升」
的过拟合拐点；据此决定早停点与 epoch 数。

**最便宜的第一步**：回到 800 条，只把 2 epoch 改 1 epoch —— 若 3k×1epoch 就好，
是过训；若仍差，是伪影。**这一步不用改代码、13 分钟。**

### ★ D12. 训练语料的预处理与精选

**依据**：v031（800 条）优于 v032（3000 条）**0.00654**，说明当前瓶颈已从
「数据量」转为「**数据保真度**」。已知的两个画像缺口：
- 段长中位 **1.63s vs 目标 1.91s**（短 15%）
- 跨 session 拼接的声学跳变（`simulate_conv.py` 文档自列为 SM 的已知缺陷）

**候选**：修段长偏差；提高 `--same-session-ratio`（现 0.3）减少拼接跳变；
按质量筛选合成样本而非全量喂入。

### D13. 多模型取长补短的集成

**现状**：已有 MOSS（端到端）/ FireRed（文本强）/ fun-asr（与 CAM 段同源）/ CAM++（分割）
四个系统，但集成方式很粗 —— 文本轴只在 MOSS 段内二选一，选源轴是整份二选一。

⚠️ **必须先读 [[text-segmentation-coupling]]**：跨分割搬文本已三次证否，
**文本与分割必须同源**。这条约束大幅限制了可行的集成形态。

### ★ D14. 调换顺序：先选源，再在选定的段上做词级仲裁

**问题**：现在顺序是「MOSS 段上做词级仲裁 → 逐 session 整份选源」，
于是选中 CAM 的 **32.5%** session 上，**仲裁成果全部作废**。

**改法**：先选源确定最终分割，**再**在该分割上跑 `fr_retext` + `word_arb`。
这样仲裁跟着最终段边界走，不会被整份替换。

**为什么它没被 [[text-segmentation-coupling]] 封死**：那页证否的是
「把 A 的成品文本搬到 B 的段上」；本方案是**在 B 的段上重新转写再仲裁**，
`fr_retext` 本来就是按任意段边界重新识别的工具，不是搬运。

**成本**：需在 CAM 段上重跑 `fr_retext` + `word_arb`（dev 约 1 小时，test 约 1.5 小时）。
**验证口径**：只需比较「选中 CAM 的那批 session」改造前后的错误数，不必全量重跑。

### ★ D5.1 MOSS + CAM++ 按段择优集成（**主线，v011**）
- **机制**：v008 实测 per-reco 互补性强，**oracle 按段择优上界 14.73%（全 dev）**。用无 ref 启发式兑现其中一部分。
- **✅ v011 = 双症状并集**：`CAM++判≥3人` 且（`MOSS判≤2人` 或 `MOSS切换率≤0.10`）→ 改用 CAM++。dev **18.39% → 16.98%（−1.41 点）**，train/holdout/全dev **三切分全胜**。脚本 `src/pick_ensemble.py`。
- **核心洞察：MOSS「并人」有两个独立症状，一段可能只显其一**。①自称人数少；②**说话人切换率塌陷**（本该交替的段变成同一标签）。症状②不依赖它自称几人，因此能抓到「真 5 人但 MOSS 判 3 人」这类 —— 症状①**结构上够不着**。dev 触发 33 段中，只靠症状② 的有 23 段。
- **佐证门槛不可省**：两条症状都要求 CAM++ 独立认为 ≥3 人。单条件 R1（只看 MOSS≤2）dev 触发 17.9% 但 test 26.4%，且 47% 的触发是误伤 MOSS 判对的真 2 人段。加门槛后 dev/test 触发率吻合（v011 为 31.1%/31.2%）。**要求两个独立系统同时表态 = 廉价的置信度代理**。
- **方法论**：train 81 挑规则 / holdout 25 验收（分层，seed=0）+ 嵌套 CV（每折在其余折选规则）。**两条规则被这道关卡拦下**：R2（段数≤5）train −0.44 但 holdout +0.07；R3（只用症状②）train 比 v010 好 0.71 但 holdout 差 0.81。
- **⚠️ 统计效力**：holdout 仅 25 段，自助重采样显示 v011 优于 v010 的 95% 区间 [−3.06, +1.34] **含 0，未达显著**。采信依据是「三切分方向一致 + dev/test 触发率吻合」的结构性证据，不是单个数字。
- **🔴 线上实测（2026-08-01）：0.16379，只破 v007 的 0.214 点，迁移率仅 15%**（dev 上是 1.41 点）。
  **不是过拟合**——test 触发率 31.2% 与 dev 31.1% 完全吻合，规则触发得对，只是触发后没赚到钱。
  真因是 **dev 收益重尾**：dev 净省 274 错误中前 3 段占 85%，剔除后 dev 收益 −0.21 点 ≈ 实际线上 −0.214 点。
  详见 `wiki/insights/dev-online-transfer.md`。
- **🔴 轴判定：对目标而言结构性耗尽**。oracle 上界 14.73%（总空间 3.66 点）同样高度集中——前 10 段占 77.8%。
  剩余 2.25 点按 15% 迁移 → 线上仅 0.34 点 → 16.04%，**距榜首 0.15023 仍差 1.02 点**。
  **即便做出完美 oracle 选择器也够不到榜首。**
- **状态**：**不再作为主攻**。v011 是该轴收官版本（线上 0.16379，当前最佳）。未试的时间轴级分歧度 /
  第三源即便成功也被上述上界卡死，不值得再投入。
- **置信度**：高（判定基于线上实测 + oracle 收益集中度分布，非推测）。

### ❌ D5.3 微调 MOSS 0.9B（**证伪封死**，两次线上验证）
- **🔴 v013 干净单变量实验（2026-08-01）**：微调 ck84 + **fp32** + 同一择优规则 vs v011（基座 + fp32 +
  同一规则），**只差模型权重一个变量**。结果 **0.16872 vs 0.16379 → 微调让线上差 0.49 点**，
  而 holdout 上微调好 0.92 点。**符号再次翻转，且这次没有混淆变量可以甩锅。**
- **根因（holdout fp32 逐组诊断）**：微调的收益只来自「基座漏判说话人」的段，代价却是全局的 ——
  | 分组 | 段数 | 净收益 | ins | del |
  |---|---|---|---|---|
  | 基座漏判(missed>0) | 9 | **+39** | −1 | **−38** |
  | 基座未漏判(missed=0) | 16 | +7 | **+32** ⚠️ | −21 |
  基座在 test 上平均判 3.20 人（dev 上 3.42）→ test 的漏判 headroom 更小 → 收益缩水、
  多吐插入的代价照旧 → 净负。
- **选择性使用也无效**：把 v011 双症状规则的备选从 CAM++ 换成微调模型 → holdout 19.57%，
  几乎等于全用基座（19.66%），远差于换 CAM++ 的 17.66%。**微调后的 MOSS 仍是 MOSS，
  失败模式与基座同源；CAM++ 是机制不同的聚类系统，才构成真互补。**
- **🔑 最重要的方法论结论**：**从 dev 内部切出的 holdout，无法探测 dev↔test 的分布差异**。
  train/holdout 同源于那 106 段，微调让模型更贴合 dev 的分布，而这恰恰是 test 上受损的原因。
  holdout 能防「在 train 上过拟合」，防不了「在 dev 整体上过拟合」。
- **状态**：封死。不再尝试仅用 dev 数据微调。
  （若将来试外部语料微调，属另一条路：那是让模型真变强，不是拟合 dev。）

### ❌ D5.3 微调 MOSS 0.9B（**彻底封死**，三次线上验证，三次均倒退）

**三次线上结果：**
- v012: ck108(106段) + bf16 + pick → 0.17023（vs v011 0.16379, 倒退 0.644 点）
- v013: ck84(81段) + fp32 + pick → 0.16872（倒退 0.493 点）
- v030: ck84(81段) + fp32 + **无 pick** + norm → **0.1737**（vs v028 0.15573, **倒退 1.797 点**，最严重）

**v030 的教训（2026-08-09 线上验证）：**
- v030 去掉了 pick_ensemble（排除 v013 的混淆变量），用 fp32（排除 v012 的 bf16 混淆），用验证过的 ck84（排除 v012 的 ck108 未验证问题）。
- dev 14.810% 看起来极好（-0.833 vs v028），但**线上 0.1737 倒退 1.797 点**。
- **根因 = dev 数据泄露**：checkpoint-84 在 81 段 dev 上训练。dev 评测用全 106 段，其中 81 段是训练数据。
  模型直接记住了这 81 段 → dev 分数是 memorization 假象。

- **方法论教训**：
