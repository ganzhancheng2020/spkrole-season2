# `pgrep -f <名字>` 会匹配到监控命令自身 —— 后台等待门与 pkill 双向踩雷

## 现象（两次，方向相反）

**① 等待门被自己的监控续命。** `camsweep2.sh` 用
```bash
while pgrep -f test_chain.sh >/dev/null; do sleep 60; done
```
等 test 链路结束。test 链路早已跑完（产物 106/106 齐），脚本却挂了 90 分钟。
原因：我用来查状态的 ssh 命令行里**包含字符串 `test_chain.sh`**，
`pgrep -f` 匹配的是**整条命令行**，于是每次我去"看它跑没跑"，
都恰好把等待门续命一轮。**观察行为本身构成了被观察的条件。**

**② `pkill -f` 杀掉自己。** 想停掉旧循环时执行
```bash
pkill -f camsweep2.sh
```
这条命令所在的 ssh 会话，其命令行同样含 `camsweep2.sh` → **把自己杀了**，
表现为 ssh 无任何输出返回（同一 heredoc 里正要创建的 cs3.sh 也随之静默丢失）。

## 为什么容易骗过人

失败长得不像失败：进程在、日志空、GPU 0%。
我据此推断"卡在 sleep"，**这个推断是错的**——
`/proc/<pid>/task/*/children` 里那个子进程其实是**已经在跑的 word_arb.py**，
等待门在我上一条 ssh 退出后就放行了。即：

- **日志为空 ≠ 没干活**（word_arb 的输出被 `>/dev/null` 吃掉了）
- **GPU 0% ≠ 空闲**（采样点恰在两次 GPU 调用之间）

真正被 `pkill` 破坏的是**父循环**，所以后两个 config 不会接着跑——
这才是需要修的，而不是我最初以为的"卡住"。

## 正解

- **等特定作业：按 PID 等**，别按名字：`while kill -0 <PID> 2>/dev/null; do sleep 30; done`
- 必须按名字时用**方括号自排除**：`pgrep -f "cs3[.]sh"`（正则匹配不到含字面 `cs3.sh` 的自身命令行）
- `pkill -f` 前先 `pgrep -af` **看清要杀谁**，确认列表里没有自己
- 后台脚本**别把关键输出丢进 `/dev/null`**，至少留 per-config 日志：`> cs3_${m}_${b}.log 2>&1`
- **判活看推进量**（产物文件数在涨），不看进程在不在
- 多行 heredoc 建脚本时，**先 scp 上传再执行**——同一条 ssh 里既建又杀，会一起死

## 与既有结论的关系

与 [[firered-llm-setup-traps]] 同属"症状指向错误病因"一族：
**"看起来在跑"不是证据，产物计数在涨才是。**
每个后台作业都要有一个廉价的、不依赖名字匹配的推进量探针。
